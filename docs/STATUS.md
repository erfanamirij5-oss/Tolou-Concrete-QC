# وضعیت توسعه Tolou Concrete QC

مالک محصول: مهندس عرفان امیری

مخزن: `erfanamirij5-oss/Tolou-Concrete-QC`
شاخه توسعه فعال: `feature/windows-desktop-foundation`
پلتفرم هدف: Windows Desktop / Offline

## وضعیت پایدار فعلی
- Electron + React + TypeScript + Vite با Renderer ایزوله و Preload محدود.
- SQLite محلی در `userData` با migrationهای نسخه‌دار و کنترل checksum/upgrade.
- ثبت واقعی پروژه، بتن‌ریزی، سری نمونه و نمونه‌های ۷ روزه، ۲۸ روزه و شاهد.
- گردش نتایج revision-based شامل draft/review/approval/correction/void و audit trail.
- زمان‌بندی revision-based نمونه شاهد.
- ثبت مشخصات مهندسی طرح اختلاط و مشخصات QC بتن‌ریزی.
- مشتری، منشأ بتن، آزمایشگاه خارجی، نتایج خارجی و پیوست امن با SHA-256.
- مشخصات فیزیکی مستقل برای هر Sample شامل شکل، ابعاد واقعی، جرم، حجم و جرم حجمی بتن سخت‌شده.
- رابط فارسی/RTL و ورودی تاریخ شمسی با ذخیره UTC داخلی.
- داشبورد و refresh هماهنگ بر پایه داده واقعی SQLite.

## اصول معماری تثبیت‌شده
- Renderer دسترسی مستقیم به SQLite، فایل‌سیستم حساس یا عملیات privileged ندارد.
- Electron Main تنها مرز اجرای Application Service و persistence است.
- IPC قرارداد typed دارد و خطاهای خام زیرساخت نباید به UI نشت کنند.
- داده‌های مهندسی مهم باید deterministic، traceable، unit-safe و قابل audit باشند.
- نتیجه‌ها و داده‌های قابل اصلاح مهندسی تا حد امکان revision-based و immutable نگهداری می‌شوند.
- UTC فقط برای ذخیره‌سازی داخلی است؛ UI و فیلتر گزارش باید تاریخ شمسی/فارسی ارائه کنند.
- هیچ rule پذیرش استانداردی بدون reference/version/test وارد production نمی‌شود.

## الزامات قطعی Analytics و Reporting
### موتور گزارش‌گیری دوره‌ای / Periodic QC Reporting
یک موتور مشترک برای سامانه QC و داشبورد مدیریت ساخته شود که کاربر بتواند بازه زمانی را انتخاب کند؛ از جمله:
- فصل شمسی
- ماه شمسی
- سال شمسی
- بازه سفارشی از تاریخ تا تاریخ

فیلترهای قابل ترکیب باید حداقل شامل این موارد باشند:
- شرکت
- پروژه
- بتن‌ریزی / Pour
- طرح اختلاط و revision آن
- منشأ بتن
- آزمایشگاه
- نوع سری داخلی/مشتری
- سن آزمون شامل ۷ روز، ۲۸ روز، شاهد و سایر سن‌ها
- بازه زمانی انتخابی

### گزارش‌های تخصصی مستقل
برای هر شاخص، گزارش و تحلیل مستقل با نمودار اختصاصی تولید شود:
1. مقاومت فشاری
   - روند زمانی نتایج
   - تفکیک ۷ روز، ۲۸ روز، شاهد و سایر سن‌ها
   - میانگین، حداقل، حداکثر، تعداد نتایج، انحراف معیار و ضریب تغییرات در صورت کفایت داده
   - مقایسه پروژه، طرح اختلاط، منشأ و دوره‌های زمانی
   - هیچ قاعده قبولی/رد استانداردی بدون Standard Profile معتبر اعمال نشود.

2. اسلامپ بتن تازه
   - روند زمانی
   - میانگین، حداقل، حداکثر و پراکندگی
   - مقایسه پروژه/طرح/منشأ/بازه زمانی
   - توزیع و فراوانی مقادیر

3. دمای بتن
   - روند زمانی دمای بتن تازه
   - میانگین، حداقل، حداکثر و پراکندگی
   - تحلیل تغییرات در طول فصل/ماه و مقایسه پروژه‌ها یا منابع

4. جرم حجمی بتن سخت‌شده
   - تحلیل هر Sample به‌صورت مستقل
   - روند زمانی kg/m³
   - میانگین، حداقل، حداکثر، انحراف معیار و CV در صورت کفایت داده
   - مقایسه نمونه‌های هم‌سن، سری‌ها، پروژه‌ها و طرح‌های اختلاط
   - امکان بررسی رابطه جرم حجمی و مقاومت در Analytics پیشرفته

5. معماری باید توسعه‌پذیر باشد تا KPIهای بعدی مانند هوای بتن، زمان حمل، زمان تخلیه، حجم، برگشتی، یا سایر پارامترهای QC بدون بازطراحی موتور گزارش اضافه شوند.

### خروجی در دو سطح محصول
#### A. سامانه کنترل کیفیت
نمای فنی و جزئی برای کارشناس آزمایشگاه/QC شامل:
- داده‌های خام و قابل drill-down تا Sample
- نمودارهای تخصصی هر پارامتر
- آمار توصیفی
- فیلترهای مهندسی کامل
- امکان مشاهده رکوردهای غیرعادی و رفتن مستقیم به پرونده نمونه/سری/بتن‌ریزی
- گزارش قابل چاپ و export در مراحل Reporting

#### B. داشبورد مدیریت
نمای خلاصه مدیریتی از همان موتور داده و همان Source of Truth شامل:
- کارت‌های KPI دوره انتخابی
- نمودار روند فصل/ماه/سال
- مقایسه پروژه‌ها، طرح‌ها و منابع
- خلاصه نقاط قابل توجه و تغییرات نسبت به دوره قبل
- امکان ورود از KPI مدیریتی به گزارش تخصصی QC بدون ساخت منطق محاسباتی جداگانه

اصل معماری: داشبورد مدیریت و سامانه QC نباید دو موتور آماری مستقل داشته باشند؛ هر دو باید از یک Analytics/Application Service مشترک استفاده کنند تا اعداد در تمام صفحات و گزارش‌ها یکسان باشند.

### طراحی گزارش فصلی
«گزارش فصلی» یک preset روی موتور Periodic Reporting باشد، نه یک سیستم جدا. انتخاب فصل شمسی باید خودکار بازه شروع/پایان همان فصل را تولید کند. همان موتور برای بازه سفارشی نیز استفاده شود.

هر گزارش فصلی/دوره‌ای باید حداقل این ساختار را داشته باشد:
- مشخصات بازه و فیلترهای اعمال‌شده
- خلاصه مدیریتی دوره
- حجم داده و تعداد نمونه/آزمون معتبر
- نمودار روند پارامتر انتخابی
- آمار توصیفی
- مقایسه با دوره قبلی در صورت وجود داده هم‌ارز
- breakdown بر اساس پروژه/طرح/منشأ در صورت انتخاب کاربر
- بخش Interpretation مبتنی بر داده، با تفکیک روشن بین محاسبه آماری و قضاوت استانداردی

## بدهی‌ها و ریسک‌های باز
- مدل داده بتن تازه باید فیلدهای قابل تحلیل مانند slump و concrete temperature را به‌صورت traceable در سطح مناسب دریافت کند.
- نقش‌ها، احراز هویت، session و مجوزهای Review/Approval هنوز باید تکمیل شوند.
- backup/restore، رمزنگاری، licensing و expiration باقی است.
- گزارش A4/PDF/PNG/Excel و workflow مدیریتی باقی است.
- installer ویندوز و آزمون نصب/ارتقا باقی است.
- CSP و hardening نهایی navigation باید قبل از release تکمیل شود.

## ادامه Roadmap
۱. تکمیل مدل QC و داده‌های پایه: مشخصات بتن تازه، اسلامپ، دما، لینک پایدار مشتری/منشأ، مشخصات پروژه و سایر فیلدهای مهندسی لازم.
۲. تثبیت workflow نتایج، داده‌های فیزیکی Sample، audit و permission model.
۳. تکمیل UX فارسی/شمسی و polish رابط Liquid Glass.
۴. ایجاد Analytics Core مشترک و query/filter layer با بازه زمانی شمسی، پروژه، طرح، منشأ، آزمایشگاه و سن نمونه.
۵. پیاده‌سازی تحلیل تخصصی مستقل مقاومت، اسلامپ، دمای بتن و جرم حجمی؛ سپس KPIهای توسعه‌پذیر بعدی.
۶. پیاده‌سازی Periodic Reporting شامل preset فصلی/ماهانه/سالانه و بازه سفارشی، نمودار و مقایسه دوره‌ای.
۷. اتصال همان Analytics Core به دو مصرف‌کننده: سامانه QC فنی و داشبورد مدیریت.
۸. گزارش‌های قابل چاپ/خروجی PDF، PNG و Excel و گزارش مدیریتی دوره‌ای.
۹. backup/security/licensing.
۱۰. Windows packaging، installer، upgrade tests و release candidate.
